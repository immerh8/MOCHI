**What frozen means.** The byte layouts, identifiers, and algorithms of §1 to §5 are fixed
for suite 1, the layout rule, and parity frame v0 (payload encoding 1, record schema
version 0, descriptor constraint 1). A change to any of them is a **new** identifier (suite
2, a new payload encoding or record schema version, a new descriptor constraint) with its
own vectors, never an edit of this file. The reconstruction procedure of §6 and the
coverage of §7 are the normative behaviour of those frames; a change that alters which
bytes a reader accepts or rebuilds is the same kind of change. Prose, evidence tables,
and the benchmark may be corrected without a new identifier. The format as a whole stays
"experimental / draft-compatible" until 1.0 (spec §28): freezing R6 means no draft-era
change to this topic, not that 1.0 has shipped.

R2 (binary envelope v0). Schema: `docs/schemas/archive-descriptor-v0.cddl` constraint 1.

## 1. Suite 1 *(checked)*

| Item | Value |
|---|---|
| Suite identifier | 1 |
| Field | GF(2^8), reduction polynomial `0x11D` (x^8 + x^4 + x^3 + x^2 + 1), addition XOR |
| Coefficient | C[p][j] = 1 / (p ⊕ (128 + j)), for parity index p and data index j |
| Data shards per group, k | 1 to 128 |
| Parity shards per group, m | 1 to k |
| Property | MDS: any k of a group's k + m shards rebuild it. No coefficient is 0 or 1 |
| Protected representation | Stored bytes (§15.1); no key is needed |

Why Cauchy, and why this matrix: a systematic Cauchy code is MDS by construction
(every square submatrix of a Cauchy matrix is invertible), so no search or table of
"good" matrices is part of the format, and a second implementation needs only field
multiplication and inversion. X = {0..m−1} and Y = {128..128+k−1} are disjoint for
every allowed (k, m), and since every x < 128 ≤ y, x ⊕ y ≥ 128: no coefficient is 1,
so a parity shard is never a byte copy of a data shard.

## 2. Layout rule *(checked: constants)*

For a protected range of *L* stored bytes and parity percentage *r*:

| Constant | Value | Role |
|---|---|---|
| `TARGET_SHARDS` | 1024 | Shards aimed for: *s* starts at ⌈L / 1024⌉ |
| `SHARD_ALIGN` | 64 | *s* is a multiple of 64 |
| `MIN_SHARD` | 16384 | *s* is at least 16 KiB, unless the whole range is smaller |
| `MAX_SHARD` | 1048576 | *s* is at most 1 MiB; larger ranges use more shards |
| `MAX_DATA_SHARDS` | 128 | Data shards per group, and the first y of the matrix |
| `MIN_PERCENT` | 1 | Smallest *r* |
| `MAX_PERCENT` | 100 | Largest *r* |

- *s* = min(`MAX_SHARD`, max(⌈L / `TARGET_SHARDS`⌉↑64, min(`MIN_SHARD`, L↑64))), x↑64
  rounding up to a multiple of 64.
- *N* = ⌈L / s⌉ real data shards; shard *i* is the stored bytes [*a* + *i*·*s*, *a* +
  (*i* + 1)·*s*) ∩ [*a*, *a* + *L*), zero-padded to *s*. Padding is hashed and coded,
  never stored.
- *G* = ⌈N / 128⌉ groups; **shard *i* is in group *i* mod *G* at index *i* div *G***.
- *k* = ⌈N / G⌉; an index *j* with *j*·*G* + *g* ≥ *N* is a virtual all-zero shard.
- *m* = ⌈k · r / 100⌉.
- *G* must fit in 32 bits (a range above about 2^59 bytes is refused).

Examples (all in the vectors): *L* = 300, *r* = 10 → *s* = 320, one group, k = m = 1
(a mirror of a tiny commit, with no coefficient 1). *L* = 1 MiB, *r* = 10 → *s* = 16 KiB,
k = 64, m = 7. *L* = 1 GiB, *r* = 10 → *s* = 1 MiB, G = 8, k = 128, m = 13.

## 3. Placement *(prose; tested in `c12_redundancy.rs`)*

- Commit *n*'s range is [*a*, *b*): *a* = its parent's footer offset (0 for commit 0),
  *b* = the end of its commit frame. So it covers the parent's footer, its own objects,
  and its own commit record; commit 0's covers the descriptor.
- Its *G*·*m* parity frames follow the commit frame directly, all of one length, and
  the footer follows them: frame *j* is parity shard *j* mod *m* of group *j* div *m*.
- The writer appends them before §12.2 step 6's sync, so the footer is still written
  last; a crash before the footer leaves an eligible tail (D14).

## 4. Parity frame *(checked: offsets against an encoded frame)*

A skippable frame of kind `0x184D2A5F`. Its payload is a binary envelope v0 (R2 §2)
with payload encoding 1, record schema version 0, the identity of the commit whose
footer follows, and that commit's required features; then this parity payload
(integers unsigned little-endian):

| Offset | Size | Field |
|---|---|---|
| 0 | 16 | Signature |
| 16 | 2 | Suite |
| 18 | 2 | Parity percentage |
| 20 | 4 | Shard size |
| 24 | 8 | Range offset |
| 32 | 8 | Range length |
| 40 | 4 | Group count |
| 44 | 2 | Data shards per group |
| 46 | 2 | Parity shards per group |
| 48 | 4 | Group index |
| 52 | 4 | Parity index |
| 56 | 32·k | Data-shard hashes |
| 56 + 32·k | s | Parity shard |
| 56 + 32·k + s | 32 | Frame digest |

A frame is 8 + 80 + 8·n + 56 + 32·k + s + 32 bytes, for n required features.

**Byte strings** *(checked)*:

| Name | Bytes (hex) | Meaning |
|---|---|---|
| `PARITY_SIGNATURE` | `4d4f434849322d504152495459000000` | `MOCHI2-PARITY` ‖ 3 zero bytes: payload encoding 1's signature (registry.rs) |
| `PARITY_SHARD_DOMAIN` | `4d4f434849322d5041524954592d534841524400` | `MOCHI2-PARITY-SHARD` ‖ 0x00 (digest.rs) |
| `PARITY_FRAME_DOMAIN` | `4d4f434849322d5041524954592d4652414d4500` | `MOCHI2-PARITY-FRAME` ‖ 0x00 (digest.rs) |

## 5. Integrity and cross-checks

- **Data-shard hash** = BLAKE3(`MOCHI2-PARITY-SHARD` 0x00 ‖ the padded shard). It
  *locates* damage; it is not an integrity anchor.
- **Frame digest** = BLAKE3(`MOCHI2-PARITY-FRAME` 0x00 ‖ every frame byte before the
  digest, skippable header included). A reader checks it **before** reading any field,
  because no record references a parity frame by hash (R2 §4).
- **Decode order** (`parity::decode_frame`): one skippable frame of the parity kind
  filling the bytes; digest; binary envelope (R2: kind, version, counts, lengths,
  encoding 1 for this kind, features, schema version 0, signature); suite (unknown:
  `UNSUPPORTED_FEATURE`); the stated *s*, *G*, *k*, *m* equal the layout rule for the
  stated range and *r*; group and parity index in range; payload length.
- **Against each other and the commit** (D21 item 7): all frames of a commit share the
  layout, identity, and features, and the frames of a group share one hash table;
  identity and features equal the commit's; *a* = the parent's footer offset; *a* + *L*
  = the commit frame's end; the frames exactly fill [commit frame end, footer); *r*
  equals the descriptor's. A disagreement among frames whose digests verify is
  `PROFILE_VIOLATION`, and nothing from that commit's frames is used.
- **A rebuilt shard is used only if it hashes to its table entry**, and everything that
  reads it still checks the commit chain's hashes.

## 6. Reconstruction procedure

From the head back to commit 0 (`mochi_core::parity::scan`):

1. Take the footer at end of file if it parses (else the latest valid footer found by
   the forward scan). Parse, do not validate: its digest covers the commit frame,
   which may be what needs rebuilding.
2. Find a frame of the commit that decodes: at the commit frame's end; else, when the
   frame there has a readable header, at each position one such frame length further on;
   else at each later position holding the parity magic (at most 4,096 decode attempts in
   all). It gives the layout and the frame length; the region must hold exactly *G*·*m*
   frames.
3. Read every frame in its slot; a frame that does not decode is damaged.
4. For each group with an intact frame: hash every real data shard; a mismatch is
   damaged. A virtual shard's table entry must equal the zero shard's hash.
5. If the damaged data shards are no more than the intact parity shards, solve the
   k × k system over the first k intact shards (data before parity), and keep each
   rebuilt shard only if its hash matches. Otherwise the group is beyond capacity
   (`PARITY_CAPACITY_EXCEEDED`), and nothing in it changes.
6. Lay the rebuilt bytes over the file in memory; validate the footer and decode the
   commit record through them; apply §5's cross-checks (on failure, drop the commit's
   rebuilt bytes); continue at the parent's footer.

The walk stops, and says why, at a footer that does not validate after rebuilding, a
commit record that cannot be read, or commit 0.

## 7. Coverage and capacity (§15.1, §15.2)

| Structure | Covered by |
|---|---|
| Data chunks (plain, sealed, stream-only), catalog images, manifests, key envelopes | The writing commit's parity |
| Commit record | Its own commit's parity |
| Descriptor | Commit 0's parity |
| Footer | The next commit's parity; the **head's footer by none** |
| Parity frames | None (their own digest only) |
| Dictionaries | None written in 1.0 |

Capacity per group: any *m* damaged shards. A contiguous burst over up to about *m*·*G*
shards puts at most *m* in each group (interleaving). Never more is promised; beyond
it the result is explicit and nothing is rewritten.

## 9. Open items

Recorded in B.2.11 too; decided at the review that froze R6 (§10).

1. **The head's footer is unprotected.** A second footer copy, or the §22
   footer-history accelerator, would cover it; both change the wire format.
2. **The end of the file is the weak spot.** Truncation removes the newest parity first.
   A trailer copy or sidecar is a 1.x possibility.
3. **Hash-table overhead for small commits.** Each frame repeats 32·k bytes of hashes:
   for a 100 KB commit at 10 % that is one 16 KiB shard plus 400 bytes. An index frame
   per group would shrink it at the cost of a single point of failure.
4. **GF(2^8) bounds a group at 128 + 128 shards**; big commits use more groups instead
   of a larger field (GF(2^16) would allow larger groups and stronger scattered-damage
   tolerance per group, at several times the coding cost).
5. **No throughput benchmark.** None was claimed (§27); one belonged with the freeze and is written (`docs/benchmarks/c12-parity.md`).

The calls on these five items are in §10.

   result; the text now says what the code does. The decode-attempt bound of 4,096
   covers both.
2. **Stale status text** ("draft", "not frozen", "pending the review", "No throughput

3. **The benchmark had no hash-table figure.** K15 item 3 said "quantified by the

decided here): the multiply-add is scalar and single-threaded, so the parity phase at
50 % to 100 % is slow (21 s and 44 s for 512 MiB); a nibble-table SIMD multiply and running
groups in parallel would change no byte and the vectors would catch an error; the Encrypted
profile with parity, memory use, and other hardware are not benchmarked.
