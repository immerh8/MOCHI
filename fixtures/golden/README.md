# Golden fixtures

Valid, corrupt, and interrupted archives with their expected reports (ratification
artifact R8). The first set, `c1/`, covers the framing layer: 17 vectors (valid frames,
a valid session with a footer, and rejects for reserved blocks, oversized frames,
truncation, a bad footer digest, a bare v1.2-style trailer, a forged footer
inside a data payload, and a descriptor frame away from offset 0). They are frame-level vectors, not whole `.mochi` archives.

Rules (AGENTS.md):

- Golden files change deliberately, never by blanket regeneration. A format-affecting
  change updates the specific fixtures it affects and the PR explains each diff.
- The set includes archives with **hostile names** (for example `<img src=x onerror=…>`)
  so the desktop UI's "text only" rendering stays covered (plan D1, spec §23.3 #9).
- Fixtures are built by `mochi-testkit`, never from ambient randomness or wall-clock time.

## Format freeze (draft 2, 2026-10-12, gate G12)

The draft identifier (descriptor key 3) became **2** and the catalog's SQLite
`user_version` became **1** (plan K13, R4 decision 3). Nothing else on the wire changed.
What moved, deliberately and each by its recipe (`write_*_golden_files`, after deleting the
file the writer would otherwise refuse to overwrite):

* `b2/*descriptor*.bin` (16 files): exactly **one byte** each (key 3's value, 1 → 2), nothing
  else. `reject-descriptor-draft-2.bin` was removed: draft 2 is now the valid value. Its
  place is taken by `reject-descriptor-draft-1.bin` (the pre-freeze draft) and
  `reject-descriptor-draft-3.bin` (a later draft). `descriptor-vectors.txt` lists them.
* `b2/reject-archive-draft-1.mochi` (new): the pre-freeze `c5/valid-archive-3-commits.mochi`
  **byte for byte**. A draft-2 build refuses it: `UNSUPPORTED_FEATURE`, exit 4, the message
  names draft 1 (`mochi-cli` test `a_draft_1_archive_is_refused_exit_4_naming_the_draft`).
* `c3/valid-catalog-v0.sqlite`: **one byte** differs (offset 63, `user_version` 0 → 1). The
  file name keeps "v0".
* `c5`, `c10`, `c11`, `c12` whole archives: same sizes. The first difference is at offset 49
  (descriptor key 3); every later difference follows from it: the descriptor's stored-object
  hash in each commit (key 10), the commit IDs and footers that cover it, the delta-manifest
  parent hashes, the image's `user_version` byte, and the offsets that did not move. In
  `c11` all sealed bytes differ because that archive is built with OS-random nonces, salts,
  and data key; it is checked by behaviour (it must keep verifying, keyed and keyless). The
  `c12` damaged pair were rebuilt from the valid archive by the same recipe, and
  `damage_within_capacity_rebuilds_to_the_valid_archive` still asserts a byte-for-byte rebuild.
  The 23 `c5` archive vectors in `c5/vectors.txt` were regenerated by their recipes
  (`write_c5_archive_vectors`); `valid-archive-3-commits.mochi` by `write_c5_golden_files`.
* **Unchanged**: every frame-level vector in `c1`, `c2`, `c4`, and `c5/*.bin` (hand-built, no
  descriptor hash inside, so the three commit IDs of R3 §4 are the same), every `b2` envelope
  vector (they use a test-local schema 0), the `c10` TAR files, the `c11` and `c12` frame
  vectors, and the two archives older than draft 2 that are frozen as first written:
  `c5/reject-archive-legacy-v0.mochi` and `c5/reject-archive-bare-image.mochi`. The latter's
  own rule (an image outside an envelope) can no longer be reached through that archive
  because its descriptor says draft 1; the rule is held by `t17_unsupported_image_does_not_fall_back`
  (a bare image forged into a draft-2 archive) and `mochi-core`'s
  `a_bare_image_is_unsupported_not_damage`.

## R8: the whole-archive golden set (gate G13)

`r8/` is ratification artifact R8 (plan W16, K21): 76 cases built on the frozen draft-2
format, with a coverage test. Valid, corrupt, and interrupted archives for every 1.0
profile and allowed combination (Core, TAR, Encrypted, Redundancy, TAR+Redundancy,
Encrypted+Redundancy), plus copy, salvage, and legacy cases. 9.6 MiB in all; the budget
is 12 MiB and a test enforces it. Tests: `crates/mochi-testkit/tests/r8_golden.rs`;
recipes: `tests/r8_golden/`; summary producer: `mochi_testkit::interop`.

Files:

* `cases.json`: the index, one object per case: `name`, `profile`
  (`core|tar|enc|red|tar+red|enc+red`), `class` (`valid|corrupt|interrupted|copy|salvage|legacy`),
  `fault` (one sentence), `spec` (sections), `fault_matrix_row` (the spec 24.2 row, or null),
  `passphrase` (the test passphrase the case is read with, or null), `expected_head` (the
  commit ID a freshness case is told to expect, or null), `copies` (file names), `salvage`
  (whether `repair plan` runs with the salvage scan), and `expect`:
  `{verify_exit, verify_level, repair_outcome, repair_exit}`.
* `<case>.mochi`, and `<case>.copyN.mochi` for copy cases (N from 1, in `--copy` order).
* `<case>.summary.json`: the expected `mochi-interop-summary-v1` (plan W17), produced by
  Rust and reviewed. The independent verifier (R9) must produce the same JSON.
* `g1/`: the G1 audit vectors (below).

**What `expect` is.** `verify_exit` and `verify_level` are `verify` at `restoration` with
`--deep` (what `fsck` asks for), reading with the case's passphrase and, for a freshness case,
the expected head. `repair_outcome` and `repair_exit` are the outcome of `repair plan`
(with the case's copies, and `--salvage` where `salvage` is true): `complete`, `partial`,
`nothing_recoverable`, or `error:CODE` with the exit that code gives (3 operational, 4
unsupported, 1 violation).

**Frozen when written.** Archives contain zstd and SQLite output, and the Encrypted writer
draws its nonces, salts, and data key from the OS (it has no injection point for a fixed
stream, and adding one for tests would change production code), so none can be compared with a
fresh build. `write_r8_golden_files` (ignored) writes only *missing* files and refuses to
overwrite one that differs; a case derived from another reads the other **from disk**. The
ordinary tests rebuild nothing: they check, for every case, that this build's `verify` exit,
repair outcome, and summary equal `cases.json` and the stored summary. Adding a case means
adding its recipe and spec, deleting `cases.json` (deliberately), and running the writer.
Regeneration of existing files happens only at a draft bump or the 1.0 flip, with an
explained diff.

**Coverage is a test, not prose** (`coverage_*` in `r8_golden.rs`). It fails if a profile lacks
a valid, corrupt, or interrupted case; if a spec 24.2 row about archive bytes in 1.0 has no
case (the rows with none are listed in the test with the reason: inventory and Preservation,
restore on a clean machine, search indexes, and the concurrency rows); or if a violation-class
error code appears in no case's summary (as the head's refusal or a finding). Three codes are
exempt, each with its reason in the test: `CHECKPOINT_MISMATCH` (raised only while writing,
`compact`, or `repair apply`, which re-read what they just wrote), `RETENTION_UNRESOLVED`
(reported by `gc plan` and `repair`, not by `verify`), and `IDENTITY_CONFLICT` (a writer-side
code: a reader that applies manifests meets the duplicate first as `RECORD_INVALID`, which
`core-corrupt-reused-chunk-id` shows).

Other tests: `truncation_at_every_byte_of_the_small_case_accepts_no_foreign_commit` cuts
`core-valid-small` at every length and requires every head found to be one of the original's
commits, at its own footer offset; `history_summaries_agree_with_the_script` and
`hostile_names_are_kept_as_bytes` compare summaries with expectations written from the
scripts, not from a reader.

### R8 summaries (`mochi-interop-summary-v1`)

The format is plan W17's. These are the rules the reference follows where W17 leaves room,
so that an independent reader can match them exactly:

* `head`: `{"status": "opened", "code": null}`, or `{"status": "refused", "code": "<R7 code>"}`
  when the head cannot be opened (the code `open_head` fails with; a wrong passphrase is
  `KEY_UNAVAILABLE`). **Addition:** an Encrypted archive read with *no* passphrase has
  `{"status": "keyless", "code": null}`; its `commits` are listed (commit records are
  plaintext) and `snapshots` is `null` (names and content are not readable). A refused head
  has `archive_id` null, `commits` and `snapshots` empty.
* `commits`: the verified chain, ascending, from the head down to commit 0, with each commit's
  footer offset and whether it is a checkpoint. `snapshots`: **one entry per commit of that
  chain whose catalog opens**. Expiry (retention) does not remove a snapshot: it only marks
  it collectable, and a collected snapshot is not in the archive at all (GC writes a new
  archive).
* `entries` are sorted by path bytes. There is no `symlink` kind in 1.0 (R4 reserves it; a
  manifest carrying it is refused), so `kind` is `file` or `dir` and `target` is always null.
  `size` is the logical length (0 for a directory); `content_hash` is the plain-BLAKE3
  file-content hash (null for a directory). `attributes` are the promised ones as recorded
  (`posix_mode`, `uid`, `gid`, `mtime_ns` = seconds x 10^9 + nanoseconds, `windows` the bits
  or null); a field not recorded, or a commit whose manifests cannot be replayed, gives null.
* `findings`: the violation-class codes of R7 section 6 that `verify` reports (any severity
  but information), plus the head's refusal code, one `{code, object}` per code. `object` is
  the **stored-object hash of a damaged data object** (a chunk of the head's catalog whose
  stored bytes fail their recorded length or hash, or that decode to the wrong content, or
  fail their AEAD tag) for `STORED_INTEGRITY_FAILED` and `CONTENT_INTEGRITY_FAILED`; a code
  with no such object appears once with `object` null. Sorted by code, then object.
  **[Clarified, W18 (R9), 2026-10-13]** The rule is per code: a code that has a damaged-chunk
  row has no null row, and damage to any other object (a manifest, a catalog image, a key
  envelope, a data region, a parity frame) never names an object. The refused summary of a
  wrong passphrase is `{"status": "refused", "code": "KEY_UNAVAILABLE"}` with that one finding:
  the summary is how R9 expresses the operational refusal, not a verification verdict. A
  keyless summary takes `profile` from the plaintext descriptor (an Encrypted archive says so).
* `parity`: null without a recovery record; otherwise the number of commits scanned
  (every commit the scan reaches counts, whether or not one of its frames decodes),
  data shards found damaged, shards rebuilt, and groups beyond capacity. **The chain and
  snapshots are read through the parity-healed view** (damage within capacity is rebuilt in
  memory, as `verify` does); `findings` still report the raw bytes.
* An interrupted publication's bytes after the head are not in the summary except as the
  `FOOTER_INVALID` / `TAIL_UNRESOLVED` findings `verify` gives them.

### The cases

Valid (21): `core-valid-{small,history,hostile-names,retention,compacted,gc,self-containing,false-magic}`,
`tar-valid-{history,hostile-names}`, `enc-valid-{history,hostile-names,rekeyed,reencrypted,keyless}`,
`red-valid-{50pct,5pct,100pct,multigroup}`, `tar-red-valid-history`, `enc-red-valid-history`.
`core-valid-false-magic` is a valid archive: a file's payload embeds a real footer frame and
a frame header, and nothing in a payload is a frame. `enc-valid-keyless` is the Encrypted archive
verified without its passphrase (exit 2, content fields null). `red-valid-multigroup` holds
3 MiB of incompressible data in one commit: more than one parity group, and the largest file in
the set. `core-valid-self-containing` stores a raw copy of another archive as a file.

Corrupt (38), one defect each: flipped chunks (head-only, older-only; also in TAR and
Encrypted), all catalog images destroyed, a middle delta manifest, the latest footer, the
descriptor, a middle commit frame, an oversized frame size (referenced, and after the head),
non-canonical CBOR in a hash-covered head commit, a dictionary dependency and a missing
dictionary, a content-hash mismatch, a traversal path, an older valid archive substituted
(`expected_head`), a truncated history, a snapshot manifest bound to another commit, an
orphan put, short extents, an undefined version, a reused chunk ID, a catalog image with a
zeroed page, a manifest that is not a frame and one cut short; TAR: an altered, re-hashed
stream; Encrypted: wrong passphrase (exit 3), a chunk sealed under another key (AEAD tag),
key envelopes out of order or duplicated, a data region that is not data; Redundancy:
within capacity, beyond capacity, a damaged parity frame, a forged parity frame (also
TAR+Redundancy within, Encrypted+Redundancy beyond).

Interrupted (10), by the spec 12.2 order, cut with the simulated storage's halt and torn-write
faults (`KeepAll`: what a fresh process finds after a kill): after the data objects, after the
commit frame, a torn footer, a lost write (the second half of a referenced chunk reads back as
zeros), after the parity frames (Redundancy), an Encrypted case, a TAR case, and a compaction
output cut before its last footer.

Copy (3, W11 tests 1 to 3), salvage (3, W12 tests 1, 2, and 4), legacy (1, the draft-1
reject).

### The G1 audit (`r8/g1/`, spec B.2.6 G1; R2 decision 4)

R3 section 7.2 listed 22 positions and 10 rules without a golden vector. The audit adds 48
vectors, each an edit of a valid golden record: `g1/vectors.txt` lists the verdict of each
(`valid`, or `rejects CODE (schema|semantic)`). `the_g1_audit_vectors_match_their_files_and_verdicts`
requires, for every vector, that the file equals its builder, that the production decoder gives
exactly that verdict, and that the CDDL schema rejects it when it is `(schema)` and accepts it
when it is `valid` or `(semantic)`. Covered: descriptor (a feature that is not an unsigned
integer, a percentage of 0 and 101, an unknown suite, Encrypted with TAR, and two valid
variants); commit schema 1 (short archive ID, short parent ID, nanoseconds, object references,
schema 1 listing feature 1, a valid time); commit schema 2 (a valid head, no or too many
envelopes, a short data region, no feature); manifest schema 1 (archive ID, chunk encoding,
protection, hash, directory with a hash or extents, a hole with a chunk offset, nanoseconds,
operation kind, entry shape, unsorted chunks, entries, and dependencies, the seconds range,
and a valid dependency); schema 2 (a valid `release`); schema 3 (a valid re-encryption
delta(0) from the Encrypted archive's plaintext, a short key-operation ID, 33 operations, two
provenance reasons); key envelope (nonce, wrapped key, salt, envelope ID, key ID sizes; suite,
KDF, features). The rules that need an archive rather than a record are R8 cases:
`enc-corrupt-envelopes-unordered`, `enc-corrupt-envelope-duplicate`,
`enc-corrupt-data-region-kind` (commit schema 2 keys 11 and 12), `core-corrupt-short-extents`
(extents that do not cover the length are refused when the manifest is *applied* to a
catalog, not when it is decoded: the audit found that `Manifest::decode` accepts them, while
R3 section 7.1 names `manifest.rs` as well as `catalog/extent.rs` as the place; no byte
changes, and the rule is held), and the key-operation replay rules, which
`c11_forged.rs` and `c11_rekey.rs` hold. Not archive bytes, so out of R8: the tail-quarantine
sidecar (a tool file, R3 Appendix A; `t24_quarantine.rs`). With the audit complete, spec 8.3's
"evidence pending" marker is removed.

Commit record **schema 1** (`docs/schemas/commit-record-v1.cddl`; plan T8).

`c5/*.bin`: 26 commit records, each one complete stored frame. Valid: a root
checkpoint, a child checkpoint linked by commit ID, and a delta on base (the

consumed. Body edits recompute the
stored ID so each reject exercises its own rule. `vectors.txt` lists each
valid vector's commit ID and each reject's error code.

`reject-commit-legacy-v0.bin` is byte-identical to the schema-0
`valid-commit-root.bin` it replaces: the builder reconstructs it from the v0
CDDL, and that identity was checked when the set was regenerated.

`c5/valid-archive-3-commits.mochi`: the scripted 3-commit history from
`mochi_testkit::archive`, written by the schema-1 writer (descriptor at
offset 0; every commit a checkpoint binding delta manifest, snapshot
manifest, and image). Like the C3 image it must **keep opening** to the
expected state at every commit, and is not compared with a fresh build byte
for byte (it contains zstd and SQLite output). Regenerate deliberately with
`cargo test -p mochi-testkit --test c5_golden -- --ignored write_c5_golden_files`.

T10 regenerated `valid-archive-3-commits.mochi` (152,028 → 152,268 bytes):
each catalog image is now binary envelope v0 + SQLite image (+80 bytes each,
n = 0). Data frames are byte-identical; every frame after the first image
moves by 80 per earlier image, so the stored offsets recorded in later
catalogs and manifests change, and with them the delta-manifest parent
hashes, commit IDs, and footers. The `.bin` commit vectors are hand-built and
did not change.

`c5/reject-archive-bare-image.mochi`: the schema-1 archive as checked in at
T8/T9, before T10, **frozen**. Its images are bare SQLite. Head location and
the commit chain must still work; opening any commit must be refused at the
image envelope (`UNSUPPORTED_FEATURE`: envelope version 0x6574), never handed
to SQLite.

`c5/reject-archive-legacy-v0.mochi`: the schema-0 archive checked in at C5,
**frozen** (the write function never touches it). Head location must still
succeed on it, and opening must refuse it as legacy (`UNSUPPORTED_FEATURE`,
spec §26).

**T11/T12 archive vectors** (`docs/t11-t12-acceptance.md`, "Fixtures"),
built by `mochi_testkit::golden::c5_archive_vectors` and listed after the
commit vectors in `c5/vectors.txt` with their expected outcome at
`open_head`: `valid-archive-delta-segment.mochi` (checkpoint, three deltas,
checkpoint, one delta; every commit opens to `c5_segment_history`),
`valid-archive-wrong-base-hint.mochi` (decision 17: opens, mismatch
reported), and 14 `reject-archive-*.mochi`: one per rejecting T11 row and
per T12 parent-link (Q22), duplicate-ID, and unknown-feature case, plus
`reject-archive-parent-offset-no-footer.mochi` (D10.6 as amended, Q23: a
parent traversal offset that resolves to no valid footer is
`FOOTER_INVALID`; added 2026-10-04, distinct from the base-footer hint). Each
reject changes one rule relative to a valid writer-produced archive, by
appending forged commits (`mochi_testkit::forge`). **Frozen** when first
written: `write_c5_archive_vectors` creates only missing files and never
overwrites an existing one,
and `write_c5_golden_files` does not touch them. Checked by behaviour, on
the frozen file and on a fresh build. Deliberately not included: the
unknown-operation case (not in the acceptance list).

**G1 additions (2026-10-05, T30).** Seven more `reject-archive-*.mochi`,
appended to `vectors.txt` so earlier lines are unchanged. They give the D11
obligations that bind a CBOR record to its commit an archive-level vector:

reject per CBOR record type (`c5/reject-commit-…`, `c4/reject-manifest-…`,
`b2/reject-descriptor-…`): a byte after the CBOR item inside the frame,
D11 "Payload length".

## C3 vector

`c3/valid-catalog-v0.sqlite`: a published catalog image with three commits (a
directory and a sparse file with a hole; a Windows name with an unpaired
surrogate; a rename). `crates/mochi-testkit/tests/c3_golden.rs` requires that
it keeps opening, verifying, and replaying to the expected snapshot at every
commit. It is deliberately **not** compared byte-for-byte with a fresh build:
SQLite may lay out pages differently in a later version, and that is not a
format change. Losing the ability to read this file would be one.

## C2 vectors

Built by `mochi_testkit::golden::{c2_object_vectors, c2_digest_vectors,
render_c2_manifest}`; checked by `crates/mochi-testkit/tests/c2_golden.rs`.

- `*.bin`: 13 hand-built single-object frames. Valid: raw, RLE, two-block, empty,
  each with content size and checksum (plan O21). Rejects: missing content size,
  missing checksum, block larger than a single-segment window, declared-size
  mismatch, overlong output, bad checksum, frame dictionary ID with no
  dictionary dependency, trailing frame, skippable frame. Never libzstd
  compressor output, so they do not change with the zstd library version.
  Checksums were computed independently (python `xxhash`) and are confirmed by
  libzstd accepting every valid vector.
- `vectors.txt`: 15 digest known answers (5 scopes × empty, `abc`, 1025 bytes)
  and each object vector's record length and expected outcome. `file-content`
  is plain BLAKE3 and matches `b3sum` (O20); the other separators are draft
  (R3).

The test recomputes every known answer from separator strings written out
literally, so a changed constant fails twice: in the file diff and in the
recomputation. Regenerate deliberately with
`cargo test -p mochi-testkit --test c2_golden -- --ignored write_c2_golden_files`.

## C10 vectors

TAR-compatible profile (spec Annex B.2.9 D19; plan C10).

`c10/*.tar`: two valid streams (`valid-basic`, `valid-pax`: a directory, files, an empty
file, a long path, a non-UTF-8 name, a time with a fraction, a large uid) and nine rejects
with one deviation each (bad checksum, non-zero padding, missing or single end block,
bytes after the end, a symbolic link, a global pax header, an unknown pax keyword, GNU
magic). Valid streams are compared **byte for byte** with the encoder's output
(`c10_golden.rs`): the encoder uses no compression library, so exactness is meaningful.
Every reject must be refused with `PROFILE_VIOLATION`, for the reason the test lists.

`c10/valid-archive-tar-4-commits.mochi`: a whole TAR-compatible archive that must keep
verifying at every level (not compared with a fresh build: it contains zstd and SQLite
output). Frozen when first written. Regenerate nothing blindly; if a deliberate format
change needs new files, delete the specific file and run
`cargo test -p mochi-testkit --test c10_golden -- --ignored write_c10_golden_files`.

## C11 vectors

Encrypted profile (spec Annex B.2.10 D20; plan C11). Written by `c11_golden.rs`.

`c11/valid-key-envelope.bin`, `valid-sealed-chunk.bin`, `valid-sealed-delta-manifest.bin`:
built with a **fixed random stream**, so they are compared byte for byte with the builders,
decode, and open with the golden key and passphrase (the envelope uses a tiny Argon2id
cost, 64 KiB, one pass, one lane). `c11/reject-*.bin` (16): one deviation each, refused with
the code `c11_golden.rs` lists: a truncated or wrong-kind envelope, hostile or invalid KDF
parameters (memory, iterations, lanes, zero lanes, memory below 8 per lane), a flipped wrapped
key, and sealed frames with a wrong version, suite, kind, key ID, nonce, ciphertext, or tag, or
too short.

`c11/valid-archive-encrypted.mochi`: a whole Encrypted archive (three commits, a rewrap, two
passphrases) that must keep verifying at every level with either passphrase, and keylessly at
`stored_integrity`. Not compared with a fresh build (zstd, SQLite, random nonces). Frozen when
first written; `write_c11_golden_files` refuses to overwrite a differing file.

## C12 vectors

Redundancy profile (spec Annex B.2.11 D21; ratification artifact R6; plan C12).
Written by `c12_golden.rs`.

`c12/valid-parity-frame.bin` and `c12/reject-parity-*.bin` (7): the frames of
`docs/ratification/R6-vectors/vectors.json` (an independent implementation's
output) as files, compared byte for byte with the JSON; each reject is refused
for its stated reason (digest, unknown suite, layout fields, signature, the
wrong payload encoding). They seed the `parity_frame` fuzz target.

`c12/valid-archive-recovery-record.mochi`: the scripted three-commit history
with a 50 % recovery record. It must keep verifying clean, and its parity must
keep decoding. `c12/damaged-within-capacity.mochi`: two data shards of commit 0
(one holds the descriptor) and two of the head damaged; the parity scan must
rebuild it to the valid archive **byte for byte**. `c12/damaged-beyond-capacity.mochi`:
three data shards of the head's group damaged, one more than its parity; it must
be reported (`PARITY_CAPACITY_EXCEEDED`) and left exactly as it is. Not compared
with a fresh build (zstd and SQLite output). Frozen when first written;
`write_c12_golden_files` refuses to overwrite a differing file.
